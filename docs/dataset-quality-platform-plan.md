# 数据集质量检查管理平台方案基线

> 状态：需求与架构方案基线
>
> 更新时间：2026-10-13
>
> 本文记录当前已经确认的业务规则、可行架构、样例分析和问题台账。未特别标注为“已确认”的内容属于建议或待核实项，不应被当作正式质检标准。

## 1. 目标与范围

平台面向公司内网的多账号浏览器用户，管理持续到达的机器人数据集，并形成以下闭环：

```text
数据接入与批次确认
  -> 固定数据版本
  -> 自动脚本检查
  -> 异常全检与正常抽样
  -> 人工初检
  -> 交叉检查与争议裁决
  -> 扩大抽检（必要时全检）
  -> 评分与管理员验收
  -> 固定交付快照与导出
```

首期数据格式为 LeRobot 和 MCAP。MCAP 支持原生检查和按数据源配置的转换后检查。数据可来自预留服务器目录、物理拷贝、本地/NFS、ModelScope、S3 兼容对象存储、FTP/FTPS 等；接入方式按数据源配置。

百万小时数据可能分批、非固定时间到达，同时支持约百名质检员。平台需要将交互式查看与后台检查、拷贝、转换、抽样和导出任务分离，任务能够重试、恢复和追溯。

## 2. 已确认的业务规则

### 2.1 组织、账号与权限

- 首期由管理员创建本地账号，并预留 LDAP/OIDC 等统一登录接口。
- 数据按项目授权。
- 质检员默认只能访问分配给自己的任务；管理员可以扩展项目浏览、复核、验收和导出权限。
- 视频播放、原始文件访问、检查结果写入和导出均在服务端执行权限校验。
- 存储凭证只在服务端使用，不进入浏览器、配置导出或交付清单。

### 2.2 数据集、批次、版本与快照

- 数据集是持续接收数据的逻辑集合，不要求一次性关闭。
- 一次物理拷贝或渠道同步形成一个接入批次。
- 批次独立执行自动检查、人工检查、评分和管理员验收。
- 数据内容变化、修复或替换会形成新的数据版本；历史版本的检查和验收记录保留。
- 交付通过时间点或交付节点生成固定快照。快照固定数据范围、检查轮次、评分快照和验收记录，不要求重复复制全部大文件。
- 数据集在所有预期批次完成前保持“持续接收/待完成”；已验收批次可以独立导出和交付。

### 2.3 接入与批次就绪

- 首期优先支持预留存储目录和物理拷贝，平台登记批次并扫描管理员允许的根目录。
- 接入目录可选择人工确认完成、完成标记/交付清单自动确认两种方式，也可按目录同时支持两种信号。
- 同一批次重复扫描、重复确认或 Worker 重试只能触发一次业务检查轮次。
- 批次在确认完整后才进入索引和自动检查；拷贝中断、文件仍在变化或清单校验失败时不能开始正式质检。
- ModelScope、S3、FTP/FTPS、NFS、本地拷贝使用统一数据源接口，渠道适配器负责发现、认证、同步和断点恢复。

### 2.4 自动检查

- 系统定期发现新增批次，管理员也可以手动触发检查。
- 自动检查使用平台内置或已部署的脚本，管理员选择脚本版本和参数；首期不要求脚本上传或在线编译。
- 脚本版本、参数、适用格式、执行范围和结果协议必须注册并保存。
- 自动检查结果区分通过、警告、失败、无法检查和执行失败；执行失败不能被当作数据通过。
- 自动检查必须保存完整的结构化 episode 发现，不依赖截断的文字报告。
- WARN 和 FAIL episodes 全部进入人工检查；脚本执行失败、未检查和无法检查进入单独的处理队列。

### 2.5 人工检查、交叉检查与扩检

- 默认以 episode 作为人工检查单元。MCAP 使用已有 episode ID 或开始/结束标记；标记来源由数据源配置。
- 每个初检任务由一名质检员完成。
- 正常 episodes 按管理员设置的比例抽样；抽样可配置分层依据、随机种子和最小样本数。
- 管理员配置交叉检查比例，并可选择独立盲检或查看初检结果的复查模式。
- 交叉检查不得分配给初检人员；盲检隐藏初检结论和初检人员信息。
- 分歧或争议提交管理员裁决，保留双方结果、证据、裁决理由和最终采用结论。
- 正常抽样发现不合格数据达到管理员配置的阈值后，平台按配置追加抽样，最终可以扩大至全检。
- 扩检按同一数据版本进行，记录每轮范围、抽样规则、触发原因、入选名单和策略版本，不重复创建已有任务。

### 2.6 检查模板与结论

- 正式质检标准通过配置文件导入或同步；管理员审核并发布版本。
- 管理员配置结构化检查项、适用条件、权重、缺陷等级、证据要求、不可通过的硬性门槛和“不适用/无法判断”规则。
- 人工可以纠正语义误报；文件损坏、关键数据缺失等硬性失败必须修复并重检。
- 自动检查原始结论永远保留；人工采纳的修正结论单独记录，并关联证据和操作人。
- 数据内容未变、人工模板未变且检查范围不受影响时，可以复用人工结果；受修复、规则变化或解释映射变化影响的部分重新检查。
- 只修改汇总权重或验收分数线时，可以复用结构化答案并重新计算评分；修改检查项、缺陷定义、MCAP topic 映射或 episode 边界时，重新判定受影响范围。

### 2.7 评分、验收与导出

- 评分模板分别配置自动检查分和人工质量分的权重，并保留硬性准入门槛。
- 模板可以选择 episode 等权或有效时长加权；抽样概率和分层比例必须进入评分快照。
- 批次达到综合评分和准入要求后，允许包含部分不合格 episodes；不合格 episodes、数量和时长必须明确展示。
- 最终验收由管理员确认通过或驳回；系统只负责验证条件和展示阻塞原因。
- 每批次独立验收和交付；数据集整体在全部范围完成前保持待完成。
- 支持全量数据和合格子集两种导出；导出清单明确 episode 范围、人工检查覆盖、自动检查状态、不合格数据和所用配置版本。
- “人工确认合格”不能包含未人工检查的 episode。其他规则筛选子集必须明确“自动通过但未人工检查”等状态。

## 3. 配置继承与发布

策略按以下顺序生效：

```text
平台基础配置 -> 项目默认 -> 接入目录覆盖 -> 批次覆盖
```

可覆盖内容包括脚本及参数、正常抽样比例、交叉检查比例与模式、扩检阈值、评分模板、硬性门槛作用范围和导出筛选规则。

建议首期支持 JSON 和 YAML 两种配置文件格式，共用一套 schema 和校验器。配置文件导入/同步流程为：

```text
读取 -> schema 校验 -> 引用与冲突检查 -> 展示差异
  -> 草稿版本 -> 管理员发布 -> 新检查轮次使用
```

建议外部同步先生成草稿，管理员发布后才生效，避免文件变化直接影响运行中的任务。每次检查轮次保存完整的最终生效配置、来源层级、配置版本、源文件摘要和发布记录。

配置校验至少包括：比例和权重范围、脚本与版本是否存在、检查项引用、硬性门槛与导出条件是否冲突、扩检是否有终止条件、适用格式和机器人类型是否匹配。

## 4. 推荐架构

当前项目的 Next.js 查看器继续承担视频、传感器曲线、轨迹、URDF 回放和现有 LeRobot doctor 的交互界面；新增平台服务和后台执行层。推荐逻辑分层如下：

```text
浏览器
  -> Next.js 平台界面/API
       -> 认证、项目权限、数据目录、任务、评分、导出
       -> PostgreSQL（业务事实、状态、审计、配置版本）
       -> 任务队列
            -> 接入/拷贝 Worker
            -> LeRobot/MCAP 索引与转换 Worker
            -> 自动检查 Worker
            -> 抽样/分配/评分 Worker
            -> 导出 Worker
       -> 文件或对象存储（预览、报告、导出分片）
  -> 受权限控制的数据访问层
       -> 本地/NFS/S3/FTP/ModelScope 等数据源
```

这是首期的架构建议，不是已锁定的中间件选型。独立 Worker 是必要的边界：doctor、视频解码、MCAP 转换和百万小时数据扫描不能依赖 Next.js 请求生命周期完成。

关键可靠性要求：

- 任务至少一次执行，业务结果按幂等键写入。
- Worker 使用租约、超时、重试和死信/人工处理状态。
- 检查轮次、任务、导出和验收使用数据库事务。
- 原始来源尽量只读；子集导出和修复在派生副本执行。
- 大文件导出和长时间检查均为后台任务，支持断点和进度查询。

## 5. 核心数据模型

```text
Project
  Account / ProjectMembership / Permission
  Dataset
    DataSource / IngestionBatch / DatasetVersion / StorageReplica
      Episode / EpisodeMapping
        CheckRun / ScriptExecution / Finding
          SamplingRound / ReviewTask / ReviewResult / Adjudication
            ScoreSnapshot / Acceptance / DeliverySnapshot / ExportJob
  QualityTemplate / QualityTemplateVersion
  AuditEvent
```

建议用“数据集 + 批次 + 数据版本 + 检查轮次 + episode”作为业务身份链。任务唯一性至少包含数据版本、检查轮次、episode 和任务类型，避免重复发现或 Worker 重试生成重复任务。

## 6. 样例数据分析

样例路径：`/home/chuang/下载/xtac-umi-g1-1-261012-lerobot/test/xtac-umi-g1-1-261012`

样例是 LeRobot v3.0，`robot_type=xtac_umi_g1`，3 个 episodes、6,493 帧、30 FPS、约 216.43 秒；包含 29 维 action/state、左右 tracker confidence、8 路视频（头部左右、腕部左右、四路触觉）。数据 Parquet 和各路视频均跨 episode 共享文件，通过 episode 行范围和视频时间范围切片。

当前项目 doctor 在该样例上得到 7 项 PASS、6 项 WARN、0 项 FAIL。WARN 主要包括 episode 0、2 的动作/位姿突变、速度限制、分布离群和 29 维动作通用提示；这些仅作为人工检查证据，不能直接作为不合格结论。

仓库 `/home/chuang/xense/xense-taccap-lerobot` 已确认的语义：

- [录制循环](/home/chuang/xense/xense-taccap-lerobot/src/lerobot/scripts/lerobot_record.py:402) 采用 shifted-frame：上一采样的 observation 与当前采样的 pose/gripper action 配对。
- 每个 episode 的第一次采样没有前置 observation，不写入；N 次有效采样通常生成 N-1 行。[写入逻辑](/home/chuang/xense/xense-taccap-lerobot/src/lerobot/scripts/lerobot_record.py:482)
- `tcp.x/y/z` 和 `head_camera.x/y/z` 单位为米；`r1..r6` 是旋转矩阵前两列的无量纲 6D 表示。[字段说明](/home/chuang/xense/xense-taccap-lerobot/src/lerobot/robots/taccap_gripper/README.md:882)
- `gripper.pos` 是归一化开度，0 表示闭合、1 表示完全打开；底层校准参考值 `gripper_open_rad` 使用弧度，但不等同于数据字段单位。[归一化实现](/home/chuang/xense/xense-taccap-lerobot/src/lerobot/robots/taccap_gripper/common.py:987)
- 样例的任务文本“1”属于测试占位；正式数据必须提供对任务行为的说明。任务是否成功、允许的失败和重试规则由质检模板配置。
- 非末行已验证满足 `action[t] = observation.state[t+1]`。末行 action 来自最后一次原始采样，不要求等于末行 state，不能跨 episode 比较。

未能在 `xense-taccap-lerobot` 当前代码中找到样例 `observation.tracker_confidence` 的 0–3 枚举定义。该字段来自样例声明的 `taccap-collector` 采集链路，暂不应把 0 直接解释为无效或用于扣分。

## 8. 分阶段实施与验收

### 阶段一：平台基础

- 本地账号、项目授权、审计记录。
- 数据集、接入目录、批次、数据版本和快照模型。
- 人工确认/完成标记两种批次就绪方式。
- LeRobot 本地目录接入和只读数据访问。

验收：未授权账号无法播放或导出数据；未确认完整的批次不会启动检查；重复确认不会产生重复轮次。

### 阶段二：自动检查与任务生成

- 脚本注册表、参数校验、版本冻结和后台执行。
- doctor 完整结构化 episode 结果。
- WARN/FAIL 全部入池、正常分层抽样、任务租约和重试。

验收：重启和 Worker 重试可恢复；所有异常 episode 都有任务或处理状态；脚本执行失败不被标记为通过。

### 阶段三：人工检查闭环

- 配置文件导入/同步、草稿和管理员发布。
- 结构化检查表、草稿、初检、盲检/复查、争议裁决。
- 正常抽样问题触发扩检，支持追加到全检。

验收：质检员只能看到授权任务；盲检不泄露初检结果；同一 episode 不重复计分；扩检记录完整。

### 阶段四：评分、验收与导出

- 自动/人工加权评分、episode/时长口径、硬性门槛。
- 批次管理员验收和固定交付快照。
- 全量、人工确认合格子集、规则筛选子集和检查报告导出。

验收：评分可以解释到配置版本和证据；批次可独立验收；清单明确不合格和未检查范围；来源数据不被导出改写。

### 阶段五：MCAP 与远端渠道

- MCAP 原生适配、转换后 LeRobot 适配、topic/时间/episode 映射。
- S3、FTP/FTPS、ModelScope 等连接器和缓存策略。
- 断点恢复、对象版本或文件校验清单。

验收：从原始来源到转换版本、检查结果和交付快照可追溯；同一版本重试不会产生重复业务结果。

## 9. 当前结论

平台可以进入详细设计和基础模块开发。已确认的业务规则不依赖已部署脚本清单、部署资源或性能目标；这些内容作为实施阶段的信息收集和容量验证项记录在问题台账中。

首条建议验证链路为：本地目录物理拷贝/登记 -> LeRobot 索引 -> 现有 doctor 结构化改造 -> WARN/FAIL 与正常抽样 -> 人工检查 -> 管理员验收 -> 质量报告与子集导出。质检规范完成后，通过配置文件发布正式模板，不需要重写任务和结果模型。
